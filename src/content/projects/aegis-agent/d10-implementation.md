## 1.设计目的

D10 将已经形成的任务图转成执行形态契约：谁承担哪个节点，角色之间允许传递哪些产物，如何验收与汇总，以及达到什么条件后停止。顶层仍分单智能体与多智能体，多智能体进一步区分协调者工作组和顺序交接。

任务图存在并行分支并不自动要求多个智能体；单个智能体也能并行调用工具。D10 默认选择满足约束的最小智能体数量。专业能力不足、执行上下文隔离或显式形态约束可以要求多智能体。模型描述的“专家角色”不产生权限。

## 2.输入与可信边界

`ShapeContext` 接收可信主体、计划 ID 与修订、D4/D5、D6、计划后 D8/D7 报告、D9 方案、逐节点 `NodeDemand` 以及可信 `DelegationGrant`。D2/D3 的目标与来源通过已形成的任务图、绑定动作和 D9 信息需求传入，无须再次调用模型理解原文。

规划器校验动作节点、验证方案、工具调用和必要信息的覆盖；逐节点能力、数据等级与来源范围必须与绑定动作和关联 D9 契约一致。上游阻断、未决、修订不一致、重复调用或缺失范围均不能成为执行计划。

目录只声明角色能力、运行身份引用、数据等级和来源范围。委派凭证另行绑定委派人、租户、角色身份、节点、权限快照和过期时间。目录与凭证由服务端注入；JSON 中的身份引用不能用于冒充企业账户。

## 3.企业策略与选择算法

版本化 `ShapePolicy` 限制允许角色、形态、最大智能体数、并发、绑定调用次数、消息数、通信字节、轮次和截止时间，另设候选搜索上限、重试上限与动态规划开关。

规划顺序为：上游覆盖检查 → 企业策略与角色目录 → 能力及委派过滤 → 有界候选枚举 → 隔离与通信检查 → 预算过滤 → 确定性排序。候选按智能体数量、通信通道数及稳定角色/节点标识排序。候选空间超过上限就返回未决，不能把截断搜索伪装成最优结论。

成本和延迟缺乏真实观测时保持 `None`。本阶段选择的是最小可行编排规模，尚未提供基于历史性能的经济成本优化。调用预算预留所有已绑定动作的最大尝试次数；通信轮次按本阶段串行协议保守预留。

## 4.三种执行形态

**单智能体**：一个执行实例覆盖全部必要动作，跨节点依赖保留在同一实例。角色不能同时占用两个节点执行上下文。单智能体内部工具并行由工具执行适配器负责。

**协调者工作组**：协调者是单独的身份与执行实例，计入智能体上限。工作结果先送协调者；跨工作角色依赖由协调者转发，禁止直接旁路通信。协调者与接收方都须具备对应数据等级、来源范围及源节点委派，并由运行时权限网关进一步确认实际可见投影。

**顺序交接**：用于 D4 已确定的链式图，根据依赖把产物传给下一个角色。最终动作所属角色负责汇总全部必要产物，其读取范围也要满足检查。

显式 `isolation_group` 表示不同执行职责需使用不同身份，同身份换两个角色名不能绕过。它不等于完全禁止协调者看到产物；若企业要求数据互不可见，应由数据权限与投影策略进一步约束通信，必要时生成经过脱敏验证的新产物和计划修订。

## 5.输出契约

`ExecutionShapePlan` 包含状态、执行形态、角色身份与节点分配、通信通道、汇总角色、必要节点、预算、失败策略、上游及策略版本、上下文摘要和计划指纹。`JoinContract` 明确全部必要节点、汇总者和必要 D6 断言。

状态分为 `planned`、`await_approval`、`indeterminate` 与 `not_applicable`。待审计划可以展示分工，但不能创建执行会话。指纹用于绑定与一致性检查，不是授权签名。形态分配引入新动作、身份、接收方或动态节点时，必须创建计划修订并重新走受影响维度。

## 6.通信与运行控制

`ExecutionShapeSession` 维护本次请求的活跃节点、调用预算、已完成产物、消息去重与通信计数，使用锁保护进程内状态。每次开始、结果交付、消息传递与最终汇总都会检查计划、策略、目录、委派及截止时间是否仍有效。

`RuntimeGuards.action` 负责用委派身份执行当前节点 D8/D7 复检、审批与义务检查；`artifact` 负责实际产物投影的访问授权及全部关联 D9 时效；`verify` 返回实际执行产生的 D6 结果。适配器故障、非明确允许结果、缺失或失败的必要断言均阻断交付。工作智能体自称“完成”不能替代验证结果。

`ShapeMessage` 绑定消息 ID、计划修订、租户、发送/接收角色、不可变产物引用、数据等级、关联需求、轮次和有效期。只允许计划声明的通道；只传输已通过验证的产物；协调者转发前必须已经接收。重复消息不重复计费，但仍重新检查权限与时效；同 ID 的不同内容会取消会话。

通信字节按完整消息描述的 UTF-8 大小加可信适配器声明的产物字节数计数，记录消息数、字节数、轮次和峰值活跃实例。它是协议计量，不是网络抓包测量；生产传输器必须检查真实大小并在发送前落实预算。

## 7.失败与动态结构

只对可信适配器明确抛出的 `RetryableReadError` 重试，且每次重新门控、计入调用预算并受尝试上限约束。写入失败不能在这里自动重放；幂等键、提交状态与补偿必须由受控执行网关处理。

角色故障、授权变化、预算耗尽或不可验证结果停止会话。内核输出明确取消/重规划原因，不在旧计划中隐式更换角色。动态任务只有企业策略允许时才可生成契约；实际扩展必须交给控制流适配器，并在预算上限内重新编译与复检。

## 8.本阶段实现与边界

`app/execution_shape/` 实现模型、角色目录、企业策略、规划器、运行控制与配置装配；示例配置不包含模型名和凭据。`run_offline()` 使用本地工作回调实际驱动静态依赖 DAG，覆盖单角色执行、角色交接和协调者路由；它是串行验收驱动，不提供真实并行性能数据。

条件守卫、反馈、等待、批量及动态扩展明确要求控制流适配器；不会被当成无条件 DAG 执行。截止时间能拒绝迟到结果，但同步 Python 回调无法被强制中断，生产适配器必须实现可取消调用、超时与外部副作用控制。

当前未接入主 Agent / HTTP / LangGraph 真实模型工作组。企业 IAM 委派、D8/D7/D9 网关、D6 验证器、消息传输和持久化状态由可信适配器接入；离线测试使用替身验证协议，不能证明外部企业系统已经接线。所有模型、验证器和额外工具调用的成本/限流还须在生产执行网关统一计量；新工具动作须进入新计划。

配置项为 `EXECUTION_ROLE_CATALOG_PATH` 与 `EXECUTION_SHAPE_POLICY_PATH`，仅显式装配使用。独立架构图见 [D10_architecture_diagram.md](D10_architecture_diagram.md)，验收与阶段记录见 [S24_d10_execution_shape.md](S24_d10_execution_shape.md)。
